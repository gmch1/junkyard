# 遥控器 BLE 抓包结果

采集日期：2026-08-26
采集设备：Xiaomi M2104K10AC / Android 13
遥控器主控：照片丝印 `FL216C0`

## 结论

遥控器已经确认使用 BLE Advertising。静置基线中不存在的两个强信号会在每次按键时同步出现，并形成约半秒的密集广播突发：

- Service Data UUID `0x08F0`，扫描地址 `10:9E:3A:10:25:5D`；
- Manufacturer ID `0x5556`，扫描地址 `59:BA:2B:D2:57:8D`。

两种广播的按键时间、RSSI 变化和发送计数完全同步，应是同一遥控器为兼容不同协议版本发送的两套帧。这一点属于基于抓包时序的推断。

主动重放已经进一步确认：本灯响应 Manufacturer ID `0x5556` 的 V1 遥控协议；只发送 `0x08F0` 帧没有效果。

`0x08F0` 数据可以由 `ha-ble-adv` 的 `remote_v31` codec 完整解码，包括 CRC、遥控器 ID、发送计数、随机 seed 和命令参数：

- codec：`remote_v31`；
- 遥控器 ID：`0x03CD8E61`；
- index：`0`；
- 本次连续发送计数：`78` 至 `138`。

`0x5556` 帧也已用相同算法逐字节解码和重新编码：

- 协议：FanLamp Remote V1 的 `arg2=0x00` 变体；
- V1 遥控器 ID：`0x000110E6`；
- index：`0`；
- Manufacturer ID：`0x5556`。

对应实现：

- <https://github.com/NicoIIT/ha-ble-adv/blob/main/custom_components/ble_adv/codecs/fanlamp.py>
- <https://github.com/NicoIIT/ha-ble-adv/blob/main/tests/codecs/test_fanlamp.py>

| 实际按键 | 解码命令 | 参数/含义 |
|---|---:|---|
| 开 | `0x10` | 主灯开 |
| 关 | `0x11` | 主灯关 |
| 亮度＋ | `0x39` 后接 `0x21` | `args=[20,0,2]`，`B+`，步进 `0.1` |
| 亮度－ | `0x39` 后接 `0x21` | `args=[40,0,2]`，`B-`，步进 `0.1` |
| 色温＋ | `0x39` 后接 `0x21` | `args=[36,0,2]`，`K+`，步进 `0.1` |
| 色温－ | `0x39` 后接 `0x21` | `args=[24,0,2]`，`K-`，步进 `0.1` |
| 夜灯 | `0x23` | 冷暖通道均为 `0.1` |
| 全光 | `0x21` | `args=[2,255,255]`，冷暖通道均为 `1.0` |
| 半光 | `0x21` | `args=[1,127,127]`，冷暖通道均为 `0.5` |

“全光/半光”为同一按键，五次测试依次解码为：全光、半光、全光、半光、全光，和实体灯表现一致。

## 主动控制验证

- 在实体遥控器最后序号为 `12` 时，手机连续发送 `13`～`17` 的 `0x08F0` 关灯帧：无效果。
- 改发 `0x5556` V1 帧：灯成功关闭，确认灯实际监听这一格式。
- 闲置后重放早期抓到的开灯帧 `78`：灯成功开启。
- 随后随机填写序号会造成间歇失效；精确发送下一号 `79` 后，灯成功关闭，App 再发 `80` 后成功开启。
- 改为持久化连续自增后，开关、亮度、色温、全亮、半亮均通过实机验证。

序号不会永久增长：字段只有一个字节。实体遥控器的一次连续实验从 `78` 增长至 `138`；闲置约 13 分钟后重新操作时从 `11`、`12` 开始，证明灯存在允许新序列开始的超时或重置机制。其精确超时时间尚未测定。App 正常使用时按 `0～255` 循环并持久保存当前值。

实体遥控器单次按键会在约 `0.4～0.58 s` 内发出 `56～88` 份相同的有效 V1 帧。Android 单路低延迟广播在 `0.9 s` 内只有约 9 份，导致预设亮度偶发漏收。可靠性验证阶段使用四路并行广播并让最终帧持续 `1.6 s`，实测全亮和半亮均可一次生效。后续为恢复实体遥控器的连续点击体验，最终帧缩短为约 `700 ms`；新点击会立即替换上一轮剩余广播。

第二次独立抓包再次验证了色温命令。实体遥控器的一次“偏暖”按键发送：

- V1/V3 序号 `107`：`0x39`，方向 `3`；V1 有效包 27 份、持续约 105 ms；
- V1/V3 序号 `108`：`0x21`，步进参数 `24`；V1 有效包 52 份、持续约 363 ms。

这与 App 的编码逐字段一致。单次实体按键的色温变化约为 10%。验证阶段曾把一次“偏冷/偏暖”实现为五个连续物理步进，实测变化明显；最终为支持连续点击，恢复为每次点击发送一个实体遥控器步进。测试双协议并发没有带来额外效果，正常 UI 仍只使用灯已验证响应的 `0x5556` V1 帧。

第三次对照抓包分别连续按了两次“亮度＋”和两次“偏暖”，用于判断连续按键是否携带不同的变化量：

| 实体操作 | 两帧发送序号 | 解码后的两帧参数 |
|---|---|---|
| 第一次亮度＋ | `157`、`158` | `0x39 / 方向 0`，随后 `0x21 / 步进 20` |
| 第二次亮度＋ | `159`、`160` | `0x39 / 方向 0`，随后 `0x21 / 步进 20` |
| 第一次偏暖 | `161`、`162` | `0x39 / 方向 3`，随后 `0x21 / 步进 24` |
| 第二次偏暖 | `163`、`164` | `0x39 / 方向 3`，随后 `0x21 / 步进 24` |

两次同方向按键的命令和步进参数完全一致；每次实体按键只把序号连续增加两次，并生成新的随机 seed、CRC 和密文。因此原始广播十六进制之间的大量字节差异不是更大的亮度或色温变化量，也不能用密文数值相减来计算步长。若希望手机一次点击变化更大，正确做法是连续发送多个完整物理步进，并让每一帧继续使用新的递增序号。该抓包同时观察到实体遥控器的序号达到 `164`，进一步证明它并不在 `125` 或 `127` 处强制回绕。
